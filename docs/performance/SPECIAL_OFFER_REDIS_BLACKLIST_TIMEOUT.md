# JWT 블랙리스트 Redis 타임아웃 — VU 1200 부하에서 실측

사용자가 붙여넣은 트러블슈팅 글("VU 200~1200 테스트 중 Redis 타임아웃으로
42% 실패, REDIS_TIMEOUT 300→2000ms로 해결, 성공률 69.5%→100%")이 이
저장소 어디에도 기록이 없어서 사실관계를 직접 실측으로 검증했다. 결론부터
말하면 **핵심 현상은 진짜였지만, 그 글의 구체적인 수치와 "해결됐다"는
결론은 재현되지 않았다.**

## 1. 조건

파티션 6 / 컨슈머 6, 앱 4vCPU, HikariCP 풀 20(이전 조사에서 확정한 안정적
구성)을 그대로 두고, 특가 6개에 VU를 33/100/200(합계 198/600/1200)으로
올려가며 `special-offer-multi-occupy-stress.js`(k6 maxDuration을 180초로
늘린 변형, 원본은 60초라 VU가 커지면 앱이 아니라 k6가 먼저 요청을 끊어버려
실패로 잘못 집계될 수 있어서 늘렸다)로 재현했다.

## 2. 1차 결과 — Redis 타임아웃 500ms(현재 기본값)

| VU 합계 | 성공률 | Redis 타임아웃 | Kafka 발행 타임아웃 |
|---|---|---|---|
| 198 | 100.0% | 0 | 0 |
| 600 | 100.0% | 0 | 0 |
| **1200** | **96.4%** (1157/1200) | **78건** | 4건 |

VU 1200에서만 실패가 나타났다. 앱 로그에서 정확히 다음 스택 트레이스를
확인했다 — 사용자 글의 진단과 정확히 일치한다:

```
org.springframework.dao.QueryTimeoutException: Redis command timed out
  at ...RedisTokenBlacklistRepository.isBlacklisted(RedisTokenBlacklistRepository.java:64)
  at ...JwtAuthenticationFilter.doFilterInternal(JwtAuthenticationFilter.java:48)
Caused by: io.lettuce.core.RedisCommandTimeoutException: Command timed out after 500 millisecond(s)
```

**다만 실패율은 3.6%였지 42%가 아니었다.** 그리고 VU 200(198)·600에서는
전혀 안 나타났다 — "200~1200 구간에서 최대 42% 하락"이라는 서술과는
규모가 다르다.

### 왜 지금 있는 Caffeine 캐시(`RedisTokenBlacklistRepository`)가 못 막았나

`isBlacklisted()`는 "블랙리스트 아님" 결과를 5초간 로컬 캐시하도록 이미
개선돼 있다. 그런데 이 부하 테스트는 VU(가상 사용자)마다 **매번 새로
회원가입·로그인해서 한 번만 요청을 보내는 구조**라, 모든 JWT의 `jti`가
서로 달라 캐시가 원천적으로 히트할 수 없다 — 이 벤치마크 자체가 캐시에
불리한 최악의 패턴이다. 실제 운영 트래픽(같은 사용자가 같은 토큰으로 여러
번 요청)이라면 이 캐시가 훨씬 더 도움이 됐을 것이다.

## 3. "해결책" 검증 — REDIS_TIMEOUT 500ms → 2000ms

같은 VU 1200 조건에서 REDIS_TIMEOUT만 2000ms로 올려 재실행했다.

| REDIS_TIMEOUT | 성공률 | Redis 타임아웃 | Kafka 발행 타임아웃 |
|---|---|---|---|
| 500ms | 96.4% (1157/1200) | 78건 | 4건 |
| **2000ms** | **93.9%** (1127/1200) | **16건** | **64건** |

**Redis 타임아웃은 78→16건으로 줄었지만, 전체 성공률은 오히려 96.4%→93.9%로
나빠졌다.** 원인은 Kafka 발행 타임아웃이 4→64건으로 급증한 것이다 —
Tomcat 스레드가 Redis 응답을 최대 2초까지 붙잡고 기다리게 되면서, 그만큼
스레드가 오래 묶여 뒤이은 Kafka 발행(`OfferOccupyEventProducer`,
3초 타임아웃)까지 밀려 타임아웃이 나는 요청이 늘어난 것으로 보인다.
**즉 타임아웃 값만 늘리는 건 병목을 Redis에서 Kafka 발행 쪽으로 옮긴
것뿐이지, 근본적으로 없앤 게 아니다.**

## 4. 원래 글과의 비교

| 글의 주장 | 실측 결과 |
|---|---|
| VU 200~1200에서 성공률 최대 42% 하락 | VU 1200에서만 3.6% 하락, 200·600은 영향 없음 |
| REDIS_TIMEOUT 300→2000ms로 성공률 69.5%→100% | 500→2000ms로 올리자 오히려 96.4%→93.9%로 악화(병목이 Kafka 발행 쪽으로 이동) |
| 원인이 `RedisTokenBlacklistRepository.isBlacklisted()`의 Redis 타임아웃 | **정확히 일치** — 실제로 재현됨 |

**결론: 이 글의 기술적 진단(Redis 타임아웃, 정확한 호출 경로)은 실제
현상과 일치했지만, 제시된 수치와 "타임아웃만 늘려서 해결했다"는 결론은
이번 실측으로 재현되지 않았다.** 오히려 이번 실측은 글 말미의 회고
("타임아웃을 늘린 건 임시방편이고 커넥션 풀을 늘리는 게 근본적"이라는
지적)를 더 강하게 뒷받침한다 — 타임아웃만 늘리면 병목이 다른 곳으로
옮겨갈 뿐이라는 게 이번에 직접 확인됐다.

## 5. 남은 과제

- Lettuce 커넥션 풀 크기(현재 `max-active: 16`)를 늘리거나, Redis 커넥션
  자체를 Tomcat 스레드 대기 없이 처리하도록 튜닝했을 때 VU 1200 실패가
  실제로 줄어드는지는 아직 확인하지 않았다 — 다음으로 확인해볼 가치가
  있다.
- 이번 벤치마크는 VU마다 신규 가입이라 블랙리스트 캐시가 무력화되는
  구조였다. 캐시가 실제로 도움이 되는 "같은 사용자 반복 요청" 패턴으로도
  별도 검증이 필요하다.

## 6. 실제 해결책 — fail-open 처리

Redis 타임아웃/커넥션 오류를 없애려는 시도(타임아웃 상향, 커넥션 풀 확장)는
둘 다 실패했다(3~4절). 진짜 문제는 "Redis가 가끔 느려지는 것" 자체가 아니라
**"Redis 오류가 인증 요청 전체를 죽이는 구조**"였다. `JwtAuthenticationFilter`가
`isBlacklisted()`를 예외 처리 없이 그대로 호출하고 있어서, Redis 예외가
필터 체인까지 그대로 튀어나가 요청이 실패했다.

### 적용한 수정

`RedisTokenBlacklistRepository.isBlacklisted()`에서 `DataAccessException`
(Redis 타임아웃·연결 실패 등 Spring Data Redis 예외의 공통 상위 타입)을
잡아 **fail-open**(블랙리스트 아님으로 간주하고 통과)하도록 변경했다.
액세스 토큰 만료가 30분이고 이 조회의 목적이 "로그아웃한 토큰 차단"이라,
Redis가 잠깐 흔들릴 때 인증된 요청 전체가 500으로 죽는 것보다는 최대
30분간 로그아웃 토큰이 통과할 수 있는 쪽이 낫다는 보안·가용성 트레이드오프
판단이다.

### 검증 결과

같은 조건(VU 1200, 파티션 6/컨슈머 6, 4vCPU, Hikari 20, REDIS_TIMEOUT·풀
전부 기본값)에서 재측정했다.

| | 수정 전 | fail-open 적용 후 |
|---|---|---|
| 성공률 | 96.4% (1157/1200) | **100.0% (1200/1200)** |
| Redis 타임아웃 발생 건수 | 78건 | 12건 (여전히 발생하지만 요청을 안 죽임) |
| Kafka 발행 타임아웃 | 4건 | 0건 |

Redis 타임아웃 자체는 이번에도 12건 발생했다 — 이 수정은 "Redis가 느려지는
것"을 막지 않는다. 대신 그게 발생해도 요청이 실패하지 않게 만들어서,
**세 번째 시도 만에 실제로 성공률 100%를 달성했다.**

### 시도했던 세 가지 비교

| 시도 | 성공률 | 비고 |
|---|---|---|
| REDIS_TIMEOUT 500ms→2000ms | 93.9% (악화) | 병목이 Kafka 발행 쪽으로 이동 |
| Lettuce 풀 16→128 | 88.4% (더 악화) | Redis는 싱글 스레드라 풀을 늘려도 처리량은 그대로, 오히려 동시 커넥션 수립 비용만 늘어난 것으로 추정 |
| **`isBlacklisted()` fail-open 처리** | **100.0%** | 원인(가끔 느려지는 Redis)을 안 없애고 "실패해도 요청은 안 죽게" 격리 |

## 7. 남은 과제

- `application-prod.yml`/`application-local.yml`의 `spring.data.redis.lettuce.pool.*`
  설정은 이번 조사에서 효과가 없었다(오히려 역효과). Spring Data Redis의
  `LettuceConnectionFactory`는 기본적으로 `shareNativeConnection=true`라
  일반 명령(GET/EXISTS 등)은 풀이 아니라 공유 커넥션 하나로 멀티플렉싱되고,
  풀은 블로킹·트랜잭션·pub/sub 전용 커넥션에만 쓰인다는 게 유력한 설명이다
  (라이브러리 소스로 직접 디컴파일 확인은 못 했지만, 실측 결과와 방향이
  일치한다). 이 설정을 유지할지 정리할지는 별도로 결정이 필요하다.
- CPU 경합 자체를 줄이는 방향(프로듀서·컨슈머 프로세스 분리, 또는 CPU
  추가 확보)도 후보로 남아있다 — 다만 이전 실측(문서 3절)에서 "총 자원이
  같으면 분리가 오히려 손해"라는 결과가 있었으니, 분리보다는 CPU 총량
  자체를 늘리는 쪽이 더 근거가 있다.
